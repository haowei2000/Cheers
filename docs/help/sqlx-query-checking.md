# Compile-time SQL query checking

Gateway application queries use SQLx 0.8 checked macros. Ordinary Cargo builds
use the committed metadata in `server/.sqlx`; they do not need PostgreSQL.
The repository's `.cargo/config.toml` defaults `SQLX_OFFLINE` to `true`, and the
Docker builder explicitly enables offline mode and copies the metadata and SQL
query files.

Use `sqlx::query!`, `sqlx::query_as!`, `sqlx::query_scalar!`, or their checked file
variants (`query_file!`, `query_file_as!`, `query_file_scalar!`). Bind values as
macro arguments. Keep SQL static: choose between checked statements for finite
variants such as sort directions, rather than assembling SQL at runtime.

## Refresh metadata after changing SQL or migrations

Install the CLI matching the locked SQLx version:

```bash
cargo install sqlx-cli --version 0.8.6 --locked --no-default-features --features rustls,postgres
```

Point `DATABASE_URL` at a disposable PostgreSQL 16 database. Do not use a
production database to prepare queries or verify migrations. From `server/`:

```bash
cargo sqlx migrate run
cargo sqlx prepare -- --all-targets --features integration
cargo sqlx prepare --check -- --all-targets --features integration
cargo check --all-targets --features integration
cargo test --features integration
```

`cargo sqlx prepare` explicitly enables online query checking even with the
repository's offline default. Commit changed query source and `.sqlx` metadata
together. Never edit an applied migration to make a query compile: add a new
migration or fix the query against the actual schema.

From the repository root, run the query API guard:

```bash
python3 scripts/check-sqlx-queries.py
```

CI runs this guard, creates the schema from migrations in a fresh database,
checks that committed metadata matches the queries and schema, compiles offline,
and runs the database-backed tests. The metadata check covers all targets and
the `integration` feature; stale or missing metadata fails CI.

## Guarantees and boundaries

Checked macros validate SQL against PostgreSQL: syntax, referenced tables and
columns, parameter count and parameter types. Typed macro results also connect
returned columns to Rust fields and types. Metadata represents a schema snapshot;
the CI online check is what keeps that snapshot aligned with migrations.

Application query results use typed fields generated by `query!`, or named
projections checked by `query_as!`. Shared converters accept those named types;
there are no `PgRow` consumers or string-based `Row::try_get` decoders in
`server/src`. The guard rejects raw row fetching and runtime row imports as well
as unchecked query construction. Test setup and intentional negative SQL tests
may continue to use runtime queries; the source guard applies to `server/src`.

Do not use unchecked macros, raw query functions, or `QueryBuilder` in application
code. Avoid parameter `as _` overrides that suppress type checking. Nullability
annotations such as `AS "count!"` must follow SQL semantics (for example `COUNT`
and `EXISTS` always return a value). Outer-join columns may need explicit nullable
annotations even when their base table column is `NOT NULL`.

Compilation does not prove business correctness, authorization, unique/foreign-key
constraint success, valid runtime values, transaction ordering, or the absence
of deadlocks. Keep integration tests for those behaviors.
